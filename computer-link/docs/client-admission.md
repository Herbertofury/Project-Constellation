# Computer-Link client admission checkpoint (2026-11-20)

**Local proof only.** The installed Windows owner can explicitly start a job-owned
stdio MCP child with one harmless `connection_status` tool. The child says that the
dot is not connected. This is distinct from the provider-neutral Python JSON-lines
diagnostics. The Rust HTTP gate/principal binding validates supplied claims but is
not an HTTP listener, authentication system, hosted MCP server or dot connection.

| Surface | Supported route | Current evidence |
| --- | --- | --- |
| Dot, native local computer | ChatGPT Desktop optional Allow access; Revoke access stops it. Local work appears as separate Work/Codex tasks. | This dot can list connected Desktop and managed environments. Desktop presence does not validate custom Computer-Link admission or override the previously observed Windows sandbox refusal. |
| ChatGPT Desktop, local thread | Desktop-only plugin with a local stdio server; install and mention in a supported locally executing thread under workspace policy. | Platform-documented and no public endpoint/tunnel required. Computer-Link is not packaged, imported, admitted or tested on this surface. Desktop-only plugin execution is not evidence it can run in a dot's cloud/root conversation. |
| ChatGPT workspace custom MCP connection | Eligible admin/owner adds custom MCP server from Plugins; ChatGPT reaches a remote configured Streamable HTTP endpoint, or supported Secure MCP Tunnel for private hosts. | No Computer-Link workspace connection or catalog match was visible to this dot. No registration exposed by its available connector tools. Do not infer that all custom apps are unsupported by dots; support/permissions must be verified for the specific connection and surface. |
| Standalone local MCP client | Start the status-only stdio bridge locally and negotiate MCP. | Disposable integrated installer and owner-to-child status already tested. Direct host spawn is not owner-tray-owned revocation unless separate lifecycle binding is built and tested. |

Next no-hosting decision: choose an eligible **local Desktop thread**, explicitly
authorize a test-only Desktop plugin admission through the supported UI, and run a
status-only compatibility acceptance before claiming integration. That route does
not meet a requirement to use the bridge directly in the dot cloud/root. If direct
dot-cloud use is mandatory, workspace owner must first verify this exact custom
connection can be enabled for the dot and choose authenticated transport/hosting
separately; current evidence does not justify deploying a server. The user has
specified a provider-independent bridge; do not assume the OpenAI tunnel is an
acceptable default.
