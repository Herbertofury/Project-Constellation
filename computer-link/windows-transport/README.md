# Experimental Windows local transport, not released

Library-only named-pipe implementation; no default listener, CLI, installation, remote endpoint or browser registration. One local fixed-size authenticated request: status/revoke by default, or a separately granted selected-file read. No desktop or write/delete capability. Explicit protected DACL grants current user only (not logon-session isolation), PIPE_REJECT_REMOTE_CLIENTS, first-instance uniqueness, random BCrypt name and 256-bit in-memory bearer. Pairing() is an internal handoff, NOT authenticated human consent/UI. Same-user hostile process protection and audited constant-time comparison are not established.

Overlapped connect/read/write wait on completion OR owner-stop event with a monotonic session deadline, max60seconds. Cancellation is requested then drained for1second before freeing buffers. If not terminal, heap-owned buffer/OVERLAPPED/event/pipe are intentionally retained and uncertainty returned; this is NOT confirmed shutdown and requires process termination before restart. No workers are spawned. Actual tray/job integration absent. Serial one-shot framing admits exactly the first33 bytes, refuses a short read, and closes after one request; it does not support streaming multiplexing or prove trailing-byte refusal. No remote operation/session revival or automatic reconnect.

Prior six Windows tests verified in run44640519123 at6d19ecac: actual local authenticated status, already-buffered request, wrong token, owner exit during pending connect, no-client expiration and peer revoke closes pipe. Those six passed on Windows Server2025; this does not establish cross-user ACL acceptance. Different-user DACL rejection, cancellation during blocked read/write, split-frame delivery, supervisor crash and UI consent remain gates before any capability or general release.

Official APIs consulted: https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights and https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex . CancelIoEx request alone is not completion; buffers must remain alive until terminal status.

Immediate TRUE I/O completion now uses returned byte count directly rather than waiting on an unchanged event; only ERROR_IO_PENDING enters completion waits. Cancellation drain refuses to free ERROR_IO_INCOMPLETE storage. Status success requires exact one-byte write. The60second deadline is enforced by serve_once, not an automatic timer on an idle unserved Server; callers must close/drop unserved sessions. No clean shutdown is claimed after unconfirmed cancellation.

Private selected-file integration candidate: separately constructed SelectedRead binds a fresh workspace and one validated leaf name. Only explicit serve_selected_read grants opcode2, returning a4byte big-endian length plus at most4096 UTF8 bytes. Requests cannot choose a path; normal serve_once still rejects opcode2. Authentication and owner-stop/deadline gates precede read, and transmission rechecks the session. No write/list/delete/admin operation is transported. Selection via API is not human consent UI or authenticated remote pairing. Synchronous filesystem read can outlive cancellation/deadline, so immediate shutdown of this added operation is NOT proven. Workspace ancestry/ACL/race limitations continue to apply, and this remains unsuitable for hostile-owner filesystem or remote exposure. Ten Windows tests authored: prior six plus four new integration cases pending execution, including wrong-token with missing selected file. Tests use only disposable synthetic local files and verify source bytes remain unchanged.

Selection binds a name, not immutable file identity or a content snapshot: selected contents may change before read. There is no guaranteed revoke-before-first-byte race boundary. SelectedRead construction currently creates the new directory before validating its leaf; it is not a pure read-only admission step. Initial root/ACL/ancestor races remain holds.
