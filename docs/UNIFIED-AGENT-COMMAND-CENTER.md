# Constellation: unified agent, account and project command center

**Status:** proposed implementation roadmap, 2026-11-28. This is a product and engineering contract, not a shipped feature or a new release. Start from the latest accepted release and reconcile the highest-versioned brain state under the existing [agent contract](../AGENTS.md). Preserve the current extension, Rust hub, Electron desktop, Agent Monitor, Computer Tools, Output Vault, Living Project Rooms, Project Brain, provider safety, backup/restore and installer/recovery behavior.

## 1. North star

Make Constellation the single local-first control plane for every project, repository, AI conversation, provider account, CLI, native desktop instance, browser profile and persistent agent a user chooses to manage. A user should be able to run three independent ChatGPT accounts, several Claude/Codex/Cursor/OpenCode/Hermes agents, multiple GitHub identities, remote bots and ordinary browser tabs simultaneously, know which project and feature each is working on, and resume work without losing requirements or accidentally duplicating changes.

Do not turn Constellation into yet another model subscription or force all work into its own editor. Bring existing authorized subscriptions, applications, repositories, local machines and remote hosts. Support ordinary non-code projects as well as coding. Prefer Windows-first full acceptance, then macOS/Linux adapters; capability differences must be explicit.

**Product differentiator:** competitors specialize in isolated coding tasks, multiple accounts, native windows or persistent bots. Constellation must connect those surfaces to its existing evidence-backed project continuity and recovery system, without breaking the original provider interfaces.

## 3. Architecture and boundaries

Keep the existing Rust native hub as the coordination and durable lifecycle authority; extend it behind versioned, authenticated local IPC. Keep the Electron desktop as the main owned UI, the existing extension as a light passive sensor, and Computer Tools as the explicitly authorized automation capability. Do not add a second competing database or browser-wide observer for the same job.

Proposed domains (names are conceptual until existing schema and module inventory are reviewed):

- Identity registry: provider, host/tenant, account, credential reference, native/browser/CLI profile and verified principal. Separate local profile IDs from external account IDs and display aliases.
- Workspace registry: project, repository, local/remote checkout, worktree, branch, host, project default account, per-agent override, and allowed scope.
- Run registry: task, feature, agent definition, runtime instance, native/web session, run/attempt, ownership lease, checkpoint, artifact, message, incident and external evidence.
- Feature ledger: requirement/acceptance IDs, parent/child features, decisions, dependencies, status history, linked chats, issues, PRs, commits, tests and release receipts.
- Adapter registry: provider capability declaration (discover, launch, attach, observe, resume, send, stop, schedule, credentials, usage, review, remote), version detection, supported commands, trust/evidence level and explicit unsupported/error states.

Use stable opaque IDs, account/host-scoped external keys, schema-versioned migrations, idempotency keys, durable event IDs and monotonic per-source sequence/order. Reconcile exact scope and actual source timestamps. Preserve existing richest-output revision and closure-order invariants. Expose bounded snapshots + incremental deltas, paginated history and indexed search; use event streams rather than fixed polling loops. Extend existing stores through reviewed migrations or a single native ownership model with explicit bridge/restore semantics; test migration and rollback on copied fixtures.

An identity assignment is not authorization. Account selection, actual provider login, Git commit author, Git fetch/push authentication, and publication permission are distinct. Resolve and verify the exact account/host/repo/worktree before side effects. Fail closed on ambiguity; never fall back to the most recent account.

## 4. Must-have product workstreams

### A. Accounts & connections — P0

One account manager for ChatGPT/Codex, Claude/Claude Code, Grok, Gemini, Cursor, Copilot, OpenCode, Hermes and others as documented interfaces permit; GitHub/GitHub Enterprise and generic Git identities; browser containers; SSH/remote hosts.

- Create, label, test, enroll, discover and retire profiles; show verified identity, connection status, last evidence, subscription/usage if a documented interface exposes it, and associated projects/runs.
- Use each runtime's supported profile/config/home directory (for example documented CLAUDE_CONFIG_DIR, Codex home, GROK_HOME or Cursor config directory; verify version and exact variable before use). Isolate session DB, config, logs, MCP credentials, environment, cookies, storage and OAuth callbacks. Store only secret references in project state, OS credential vault or equivalent reviewed scoped store for secrets. Never harvest tokens, copy existing browser cookies, persist secrets in transcripts, or export them to Drive/GitHub.
- Official login in the actual selected application/CLI; keep provider consent visible to the user. Verify returned identity and refuse cross-profile redirects. Use scoped allowlisted process environments and clear inherited credentials for sibling accounts. Distinguish profile isolation from a security sandbox.
- Project defaults, folder inheritance, explicit per-run overrides and preview before launch. Once started, bind account identity immutably to the attempt; switching means explicit safe handoff/restart, not rewriting history. Display account quota reset/unknown, and provider rate-limit state without circumventing quotas or subscription rules.
- Revoke/disconnect only the selected profile; preserve user-owned local data and existing backup preferences. No automatic sign-in, consent click, or credentials exported.

### B. Agent command center and Git — P0/P1

- Universal project/workspace sidebar, live agent tiles and virtualized list/terminal views. Launch and supervise existing supported CLIs (Claude Code, Codex, Cursor, GitHub Copilot CLI, OpenCode, Grok, Gemini, Hermes, local agents and user-defined adapters). Cursor, VS Code, Devin and other external environments get documented integration capabilities, not imaginary parity.
- Native PTY streaming with bounded scrollback, structured status when available, terminal resize, attach/detach, explicit input, stop/resume/checkpoint and recoverable exit status. Separate real provider state from inferred terminal status. Track unowned processes read-only by default; never kill an unrelated process.
- Windows-safe subprocess lifecycle (review process groups/job objects), no foreground desktop takeover. Resource-aware concurrency limits, backpressure, per-host CPU/memory budgets and crash-loop breakers.
- Inventory repos across separately authorized GitHub identities; import local checkouts and account-scoped repo metadata, issues, PRs, reviews, releases, wiki links and CI evidence. Read-only discovery by default, no bulk clone/push or auth changes without explicit user selection. Use supported Git/gh/API operations and scoped credentials, not global identity mutation. Do not equate commit name/email with authenticated account.
- One real Git worktree and branch per independently writing task. Show dirty state, branch/base SHA, changed files, conflict risk and pull-request review. Support external worktrees, local folders and multi-repo projects. Use explicit review for merge, rebase, force-push, destructive deletion and publication. Never auto-remove dirty/unmerged worktrees; attach existing work without rewriting it.
- Coordinator/worker/reviewer teams, parallel fan-out and DAG dependencies with owner leases and explicit decision gates; idempotent dispatch and bounded retries. Use source and diff overlap to warn about duplicate work, not falsely assert conflict-free integration. Prompt/messaging delivery must follow existing provider-write approval rules; managed CLI actions use explicitly authorized capability scopes.

### C. Native app and browser account workspaces — P1

- Discover installed ChatGPT, Claude, OpenCode, Cursor, VS Code and other apps; support multiple independently authenticated instances only where the specific runtime permits it. Prefer supported launch/profile flags, real apps and OS-supported window controls. Do not modify signed app packages or work around a provider's identity restrictions.
- Open as independent normal windows, grouped tabs/tiles or side-by-side where supported; clean detach restores original windows. No duplicate app install by default, no forced window reparenting when unsupported, and no focus theft. Persist only safe workspace layout and exact profile/session references. Account-specific sign-in is through the original app.
- For unsupported native multi-instance login, label unavailable and offer the existing enrolled browser profile/container route. Do not call a profile an isolated account until authenticated proof exists. Revalidate after app updates.
- Each browser/profile has its own sensor under the existing hub. Firefox containers and supported browser profiles retain independent cookie stores. Never inject into hidden pages or add always-on global observers. No provider page navigation, DOM replacement, chat submit or approval clicks without applicable existing user-approved workflow.
- Unify exact-chat status, output vault, incident review, project assignments, and deep links across all these sources. Preserve streaming, editing, uploads, branches, review banners, permission controls, regeneration and native keyboard shortcuts.

### D. Persistent agent fleet — P1/P2

- First-class local/remote Hermes and OpenClaw adapters with profile-aware lifecycle, supported gateway commands, process health, logs, resource metrics, uptime, version, restart policy, owner and task schedule. Detect gateway multiplexing and separate-service mode; prevent duplicate gateway ownership and token/port collisions.
- Support containers, SSH/remote hosts, and a secure optional remote control plane; explicitly enroll hosts and pin identity, scope network access, authenticate transport, redact logs, preserve lost-connection state. Default local-only IPC; no unauthenticated remote endpoint.
- An agent can keep running when the UI closes if the user explicitly configured persistent execution. Preserve jobs, leases, next run, attempts, cancellation, checkpoint and evidence across reboot. Stop unsent work, distinguish uncertain delivery from success, use idempotent scheduling, handle time zones/DST and backoff; never silently reissue non-idempotent work.
- Treat OpenAI Dots, Grok bots, Devin/cloud agents and hosted services as capability-gated integrations. Use officially supported APIs/CLI or user-enrolled visible observation when available; otherwise label manual/external/unsupported. Do not scrape private APIs, claim direct remote control, or create fake adapters. Hosted runtimes and locally supervised processes must have different lifecycle semantics.

### E. Organization is the flagship feature — P0/P1

The user's primary pain is scattered projects, lost requirements and overlapping contributions. Extend Living Project Rooms into the global Project Atlas. Do not build a second incompatible Project Brain.

- Discover user-approved folders, repositories, worktrees, agent sessions and browser chats; offer reviewable import and deduplication. Canonical project identity uses stable IDs and repo/host/owner evidence, not title matching alone. Support aliases, multiple repos, archives, tags, hierarchy and related projects. Unassigned items enter an inbox; never silently join unrelated private projects.
- Every project has a feature/requirement ledger, prioritized backlog, task board, dependencies, decision log, artifact vault, source citations, active agents, account assignments, latest verified commits/releases and next actions. Track planned, assigned, in progress, blocked, implemented, tested, released and verified as separate states. Store evidence for each transition and distinguish missing evidence from missing implementation.
- Universal search across authorized indexed project records, chats, specs, tasks, repos, PRs, files, sessions and historical decisions. Filters for project, account, provider, host, status, owner, time, branch, priority and feature. Use paginated/incremental queries, opt-in content capture, scoped results and metadata-only mode.
- Requirement reconciliation: turn user requests and plans into proposed feature IDs with exact source excerpts; detect duplicates, superseded requirements, dependencies, omitted requests and unverified claims. Human review confirms inferred relationships and conflicts. A project checklist must compare requested vs implemented vs tested vs released, not count a chat's assertion as completion.
- Task ownership leases, duplicate-work warnings, handoff packet with goals/constraints/current evidence/changed files/remaining checks, explicit scope and recipient account, context redaction and bounded size. Compare overlapping edits and parallel branches before integrating. Preserve independent agent opinions and evidence.
- Daily/weekly project digest, What's Changed, attention inbox, stale/blocked items, pending approvals, assigned-but-idle work, release gaps and orphaned conversations. User-configured schedules only. Resume last relevant context without assuming a hosted service supports session transfer.
- Backup/restore and portable export of non-secret project metadata, revisions and receipts; enforce per-account/project authorization, opt-in sharing, conflict review, history and recovery. Do not sync raw credential stores or private chats by default.

### F. Desktop experience and CLI-first automation — P1/P2

- One command center with Projects, Agents, Accounts, Repositories, Fleet, Inbox, Search, History and Settings; global command palette and quick launch; configurable split layouts, saved views, keyboard navigation, accessible labels and reduced motion. Retain existing Monitor/Output Vault/Computer Tools surfaces and shortcut continuity.
- Provide a versioned JSON CLI for inventory, account/profile selection, project/task discovery, agent launch/attach/status/stop, worktree creation, handoff, fleet health, and safe review operations, consistent with the Athena CLI-first contract. Machine-readable errors, dry-run/plan where meaningful, capability query, explicit target, no ambient account fallback. Add SDK/MCP only over the same authorization boundary. Do not require GUI automation for actions with supported command surfaces.
- Plugins/adapters are versioned, allowlisted and capability-scoped; no arbitrary execution from untrusted webpages or transcripts. User-controlled installation, dependency audit, update rollback and ability to disable each adapter independently.
- Performance and reliability first; avoid adding heavy frontend stacks or duplicating upstream shells. Use current Electron/Rust path unless measured migration demonstrably preserves all capabilities and improves user outcomes.

## 5. Delivery sequence (independent worktrees; one integrator)

1. **Baseline and upstream audit:** reconcile current source/release, inventory actual desktop/native/extension modules and tests; run existing verification. Establish reference pins, license notices, benchmark workloads and integration ADRs. Identify already-implemented behavior before coding.
2. **Foundation:** define identity/project/task/run IDs and adapter contracts; migration, scoped secret references and fail-closed account routing; extend existing Project Brain and IPC contracts. Build fake provider and Git remote fixtures and cross-account negative tests.
3. **First usable vertical slice:** on Windows, register two CLI account profiles and two GitHub identities, associate repos/tasks, launch agents into distinct worktrees, show status/terminal, link feature ledger and review diffs. Demonstrate restart, safe detach, wrong-account denial. Use real authorized test accounts only with consent; mocks remain labeled.
4. **Expand agent + Git UI:** role-based parallel workers, task board, search, review, handoffs, exact Git identity, external worktree discovery and feature coverage dashboard. Integrate candidate licensed upstream components only after review and benchmark.
5. **Native and browser profile isolation:** validate supported real desktop launches and browser sessions per version, with three simultaneous accounts where supported, fallback and zero-loss browser performance gate. Add layout, lifecycle, and recovery.
6. **Persistent fleet:** Hermes/OpenClaw local/remote lifecycle with scoped identities, durable schedules and health; capability-gated external bots. Add remote transports only after security review.
7. **Release qualification:** execute all existing and new verification, actual Windows installation/lifecycle, browser and native app acceptance, real account tests where authorized, Athena zero-loss optimization standard, source/asset/checksum/receipt/wiki reconciliation. Release only on accepted evidence; explicit prerelease boundaries otherwise.

Parallel contributors: identity/security; agent runtime/Orca; Git/worktrees; Project Atlas/Traycer; native apps/browser; fleet/Hermes; UX/accessibility; QA/performance/release. Each owns disjoint paths/feature IDs, has a reviewable branch and cross-review partner. Integrator reconciles shared contracts and prevents duplicate implementations. Avoid touching other work in progress.

## 6. Acceptance and comparative benchmark gates

The following are proposed acceptance targets, not measured claims. Capture exact OS/hardware, runtime versions, upstream commits, sample size, command, fixture size, raw metrics and variance. Compare enabled vs disabled extension and accepted Constellation baseline; compare competitors using equivalent work and provider subscriptions. Never trade correctness, native provider behavior or protected metrics for a speed number. If a target is infeasible, record evidence and obtain review rather than weakening the test silently.

| Scenario | Required proof |
| --- | --- |
| Multi-account | At least two independently authenticated CLI identities, two separately authorized GitHub identities on one host and three concurrent web/native accounts where supported; no cross-profile secret/session/worktree/commit leakage. Wrong identity and expired login fail closed. Report native app/provider limitations separately. |
| Parallel code | 2/6/12 agents on disjoint tasks, distinct real worktrees and account bindings, live status and correct cancellation. Duplicate claims, dirty worktree removal, concurrent base changes and merge conflict detected; no lost changes. |
| Project organization | Seed 100 projects, 1,000 repositories and 10,000 task/feature/chat metadata records; search/filter/assignment and paginated history remain responsive. Seed missing, duplicate and superseded requirements, verify reviewable reconciliation and source links. No invented completion evidence. |
| Recovery | Kill/restart owned hub and UI during runs; reconnect remote host; crash during task dispatch/approval; restart with closed sessions; verify exact scope, durable state and uncertain outcomes, no duplicate submissions or phantom agents. |
| Browser performance | Real signed-in Chrome/Edge/Opera GX/Firefox where authorized, extension disabled vs enabled and accepted baseline; long conversations (320+ and 1,000+ mounted turns where feasible), streaming, typing, scroll, file upload, new tabs, branch, consent and output recovery. Zero provider errors attributable to Constellation, zero lost or mutated messages/controls, no additional ordinary content-script provider requests, no idle polling loop or unbounded observers. Hosted unavailable capabilities clearly shown. |
| Security | Cross-account isolation, credential redaction in logs/IPC/exports, secret-inheritance denial, malicious filenames/paths/commands, OAuth callback mismatch, untrusted tool output/prompt injection, remote auth, installer rollback. ## 7. Definition of done and scope guard

The roadmap is fulfilled when one genuinely usable desktop control plane connects the user’s existing accounts, projects, sessions and agents while retaining full native/browser functionality, preserving provenance, and allowing users to locate any project, verify what features are missing, safely assign parallel tasks and resume them. Feature coverage is per provider/version and visible to the user; a checkbox, placeholder adapter or mocked integration is not delivery. Run `npm run verify` and the release-specific runtime gates under AGENTS.md before a completed implementation handoff. Apply Athena pre-release optimization and CLI-first standards. Do not manufacture a release for this planning document.

This proposal deliberately prioritizes account isolation, project organization, Git identity and reliability above cosmetic parity or speculative integrations. Current release acceptance, licensing decisions, benchmark baselines and native/hosted provider support must be independently verified by implementation owners. No source code from third-party projects has been incorporated by this roadmap.
